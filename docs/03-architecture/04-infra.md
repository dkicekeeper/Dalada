# Инфраструктура

> Обновлено 2026-11-01: как устроено на версии 1.0.0 (в App Store Казахстана). Исходный план
> (Xcode Cloud, админка на Cloudflare Pages, свой домен, два проекта Supabase) упрощён — что
> осталось на потом, сказано в разделах.

## Принципы

1. **$0, пока хватает бесплатных планов**: Supabase Free, Cloudflare R2, GitHub (репозиторий
   публичный — Actions, в том числе macOS, бесплатны).
2. **Персональные данные — в РК**: этого требует закон РК. 1.0 вышла на Supabase Cloud во
   Франкфурте; когда переезжать — открытое решение 7 в
   [05-release](../05-release/README.md#решения) (рекомендация — в первые месяцы после выхода).
3. **Переносимость.** Supabase — open source; схема и функции — в миграциях репозитория. Адрес и
   ключ бэкенда вшиты в сборку (секреты `SUPABASE_HOST` / `SUPABASE_KEY`): удалённой конфигурации
   пока нет, переезд требует новой сборки (см. «Переезд в Казахстан»).
4. **Всё воспроизводимо из репозитория:** миграции, Edge Functions, стили и сборка тайлов, сайт,
   тексты App Store и TestFlight.

## Где что живёт

| Что | Сервис | Данные |
|-----|--------|--------|
| База, вход, файлы, API, функции (`push`), фоновые задачи (pg_cron) | **Supabase Cloud Free**, регион `eu-central-1` (Франкфурт), один рабочий проект | ПД пользователей |
| Тайлы, стили, шрифты, значки карты; фото мест редакции | **Cloudflare R2**, публичный бакет (`pub-….r2.dev`, `map/config.json`); свой домен — когда будет | Без ПД |
| Резервные копии базы и фото | Cloudflare R2, закрытый бакет `dalada-backups` (после настройки, «Бэкапы» ниже) | ПД, зашифрованы age |
| Сайт: главная, политика, условия, поддержка, страницы «Поделиться» | **GitHub Pages** — `dkicekeeper.github.io/Dalada` | Без ПД (публичные места и записи браузер берёт из Supabase) |
| Модерация (жалобы, места, правки) | **Supabase Studio** — своей админки нет | — |
| Погода у места | Open-Meteo (без ключа, координаты округлены до ~1 км) | Без ПД |
| Код, CI, сборки iOS | **GitHub Actions** (macOS) → TestFlight и App Store Connect | Без ПД |

Отдельного проекта для разработки нет: миграции и тесты идут в локальном стеке (`supabase start`) и
в CI, в облако попадает только то, что прошло тесты в `main`.

## CI/CD

Всё — GitHub Actions. Репозиторий публичный, логи тоже: секреты, контакты и данные пользователей в
логи не печатаем.

| Что | Workflow | Когда и что делает |
|-----|----------|--------------------|
| База | **Supabase** | На каждое изменение `supabase/`: локальный стек → миграции с нуля → линтер → тесты pgTAP. В облако миграции применяет GitHub-интеграция Supabase при слиянии в `main` |
| Edge Functions | **Edge Functions** | Деплой `supabase/functions` при изменениях в `main` |
| iOS | **iOS** | macOS: сборка приложения и тесты пакета `DaladaKit` на ветках `claude/**` и в `main`; задача **Design lint** — токены DesignKit и отступы строк. iOS-код попадает в `main` только после зелёной сборки |
| Сборка в TestFlight | **TestFlight**, **TestFlight info** | Вручную: архив, облачная подпись, загрузка (номер сборки — 100 + номер запуска); тексты TestFlight и отправка внешним тестировщикам ([testflight.md](../04-beta/testflight.md)) |
| App Store | **App Store page**, **App Store release**, **Screenshots** | Тексты страницы, версия, анкеты, сборка к версии, скриншоты ([05-release](../05-release/README.md#выпуск-обновлений)) |
| Карта | **Map tiles**, **Editorial photos** | Тайлы из OpenStreetMap — раз в месяц и вручную; стили — при изменениях `map/`; фото мест редакции — на R2 |
| Сайт | **Pages** | При изменениях `docs/public` и сборщика, и раз в сутки (страницы публичных мест) |
| Бэкапы | **Backup** | Каждую ночь (ниже) |
| Дизайн-система | **DesignKit update** | Раз в сутки: новая версия DesignKit → сборка и тесты → в `main`, если зелёные |
| Пуши | **Push check** | Вручную: миграции в облаке, секреты функции (только имена), очередь, пробный пуш |

## Мониторинг

- **Бэкенд:** логи и отчёты Supabase (API, Postgres, Auth, Edge Functions), советник по
  производительности и безопасности в панели Supabase; пуши — workflow **Push check**.
- **iOS:** Xcode Organizer (краши, зависания) и MetricKit → закрытая таблица `private.diagnostics`
  без привязки к человеку ([05-release](../05-release/README.md#r1-витрина-и-надёжность)); отзывы о
  сбоях из TestFlight — **TestFlight info** с галочкой «crashes».
- **Метрики продукта:** SQL-функции по данным в базе, без событий и SDK аналитики
  ([M17](../04-beta/M17-metrics.md)).
- **Доступность:** внешней проверки пока нет.

## Бэкапы

Workflow **Backup** (`.github/workflows/backup.yml`, с 2026-10-09):

| Что | Как |
|-----|-----|
| База | Каждую ночь (01:41 по Алматы): `supabase db dump` — роли, схема и данные (как в инструкции Supabase «Backup and restore using the CLI») + расписание pg_cron (`cron.sql`) → **восстановление в чистый локальный Supabase** и сверка числа строк в каждой таблице с дампом (`.github/scripts/backup_check.py`) → архив, зашифрованный age → `db/` в закрытом бакете R2 |
| Фото (Storage `media`) | Раз в неделю (воскресенье) или вручную с галочкой: `rclone sync` из Storage (S3) в `media/` того же бакета — удалённые в приложении фото уходят и из копии |
| Сколько храним | 29 дней: политика конфиденциальности обещает, что копии перезаписываются в течение 30 дней |
| Чего в копии нет | Секреты из vault (`push_function_url`, `push_worker_secret`) и Edge Functions — они в репозитории и секретах |
| Код и схема | Репозиторий |

Логи публичные: workflow печатает только имена файлов, размеры и «строки совпадают». Пока настройка
не сделана, задачи пропускаются с предупреждением.

### Настройка (владелец, один раз)

1. **Бакет.** Cloudflare → R2 → Create bucket `dalada-backups`; публичный доступ **не** включать.
   Другое имя — переменная `BACKUP_BUCKET`.
2. **Доступ к бакету.** R2 → Manage API tokens: либо добавить `dalada-backups` в токен карты (тогда
   ничего больше не нужно), либо новый токен с Object Read & Write только на `dalada-backups` →
   секреты `BACKUP_R2_ACCESS_KEY_ID` и `BACKUP_R2_SECRET_ACCESS_KEY`.
3. **Ключ шифрования.** На Mac: `brew install age`, затем `age-keygen -o dalada-backup.key`. Файл
   ключа — в менеджер паролей и на флешку: без него копию не открыть. Открытый ключ (строка
   `age1…` из вывода) → GitHub → Settings → Secrets and variables → Actions → **Variables** →
   `BACKUP_AGE_RECIPIENT`.
4. **Строка подключения.** Supabase → Connect → **Session pooler** → URI, в неё — пароль базы →
   секрет `SUPABASE_DB_URL`. (Прямое подключение — только IPv6, у GitHub Actions его нет.)
5. **Фото.** Supabase → Storage → S3 Connection → включить, New access key → секреты
   `SUPABASE_S3_ACCESS_KEY_ID` и `SUPABASE_S3_SECRET_ACCESS_KEY`; регион проекта, если не
   `eu-central-1`, — переменная `SUPABASE_S3_REGION`.
6. **Проверка.** Actions → Backup → Run workflow (с галочкой «фото»): в итогах — имя копии, размер,
   «строки совпадают».

### Восстановление

1. Скачать нужный `db/dalada-db-….tar.gz.age` (R2 в панели Cloudflare или `rclone`), открыть:
   `age -d -i dalada-backup.key dalada-db-….tar.gz.age | tar xz`.
2. Новый проект Supabase (или self-hosted в РК), его строка подключения — `URL`:
   ```bash
   psql --single-transaction --variable ON_ERROR_STOP=1 --file roles.sql --file schema.sql \
     --command 'SET session_replication_role = replica' --file data.sql --dbname "$URL"
   psql "$URL" -f cron.sql
   ```
   Строки `GRANT SET ON PARAMETER` в `roles.sql` выдаёт платформа — если они не проходят, удалить их.
3. Секреты vault: `push_function_url`, `push_worker_secret` ([M6d](../04-beta/M6-beta-readiness.md)).
   Edge Functions — workflow **Edge Functions**; история миграций —
   `supabase migration repair --status applied <версии из supabase/migrations>`.
4. Фото — `rclone copy` из `media/` бакета бэкапов в Storage нового проекта.
5. В приложении — новый адрес и ключ: секреты `SUPABASE_HOST` / `SUPABASE_KEY` и новая сборка;
   пользователи один раз входят заново.

Восстановление в чистую базу проверяется каждую ночь в самом workflow, отдельная ежемесячная
проверка не нужна.

## Безопасность

- RLS на всех таблицах; чужие данные — только через RPC с огрублением координат; тесты видимости в CI
  (pgTAP); советник безопасности Supabase без предупреждений.
- Сервисный ключ (`service_role`) — только в Edge Functions, никогда в приложении, репозитории и чате.
- Секреты функций (ключ APNs) — в секретах Supabase и Vault; ключ App Store Connect, ключи R2 и
  демо-аккаунт — в секретах GitHub.
- Модерация — в Supabase Studio под аккаунтом владельца; своей админки с ролями и журналом пока нет.

| Сервис | Что получает | Зачем |
|--------|--------------|-------|

| Cloudflare | Запросы тайлов (IP-адрес); зашифрованные бэкапы базы в R2 | Карта, резервные копии |

## Переезд в Казахстан

**Когда:** решение 7 в [05-release](../05-release/README.md#решения) — рекомендация: в первые месяцы
после выхода 1.0. Начать стоит с удалённой конфигурации (адрес бэкенда, который приложение берёт с
сайта): тогда переезд не зависит от того, обновили ли все приложение.

**Куда:** self-hosted Supabase (Docker Compose) на VM в РК + S3-хранилище в РК для Storage.
Кандидаты:

| Провайдер | ЦОД | Что есть (по открытым данным) | Проверить |
|-----------|-----|-------------------------------|-----------|
| PS Cloud Services (ps.kz) | Алматы, Астана | VM, управляемые базы, S3, Kubernetes | Цены, CDN |
| Yandex Cloud, регион kz1 | Караганда | VM, Object Storage | Цены в ₸ |
| Servercore KZ | Алматы (Tier III) | VM, облачные базы, от ~3 945 ₸ за vCPU в месяц | S3 в Алматы |
| VK Cloud KZ | — | VM, базы данных | ЦОД, S3 |

Размер на старте: VM 4 vCPU / 8 ГБ / 100 ГБ SSD + S3 → ~40–80 тыс. ₸ в месяц (оценка).
На этой же VM потом живут воркер медиа (проверка NSFW, видео) и Valhalla (роутинг 1.1).

**Как (по официальной инструкции Supabase «Restore a Platform Project to Self-Hosted»):**
1. Поднять self-hosted Supabase на VM, Storage — на S3 провайдера.
2. Перенести базу через Supabase CLI: роли, схема, данные.
3. Скопировать файлы Storage (rclone), задеплоить Edge Functions, перенести секреты и pg_cron.
4. Новый адрес — в удалённой конфигурации (когда она будет) или в секретах `SUPABASE_HOST` /
   `SUPABASE_KEY` и новой сборке.
5. Пользователи **один раз входят заново** (у нового сервера другой JWT-секрет; аккаунты сохранены).
6. Удалить данные из Supabase Cloud после проверки.

**Что появится в эксплуатации:** обновления Supabase и ОС, мониторинг VM, бэкапы Postgres
(WAL-G или pgBackRest в S3). Это главная цена переезда для одного разработчика.
